# User Feedback

This document summarizes how real usage has shaped Evidence of Life. It is a
qualitative summary, not formal research.

## Honest status

Evidence of Life has been tested by **30+ early users** (31 registered accounts, including the maintainer's own, in
the current Supabase project as of October 2026) and has
evolved through direct, informal feedback — particularly around visual timeline
planning, drag-and-drop scheduling, reminders, lower-friction capture, and
map-based memory.

Early individual feedback was collected through informal direct conversations and
product testing. It was **not** consistently archived or converted into public
GitHub issues. To stay honest, the themes below are presented as a qualitative
summary rather than as quotes, retention numbers, or research metrics. No feedback
has been invented or reconstructed after the fact.

## Feedback themes and resulting changes

| What users experienced | What changed in the product |
| --- | --- |
| Lists alone did not make the day feel realistic. | Added and refined draggable timeline planning. |
| Plans changed too frequently. | Made tasks easier to move and rearrange visually. |
| Users could not understand where time went. | Strengthened planned-versus-actual and recap views. |
| Capturing moments required too much effort. | Added quicker capture, smart input, and reminders. |
| Photos and memories felt disconnected. | Connected moments and photos to map locations. |
| Users wanted a visual representation, not only lists. | Designed timeline and calendar views alongside task organization. |

## Going forward

Future feedback is handled as a repeatable, public loop rather than private
conversation. New input is captured through the
[user-feedback issue template](../.github/ISSUE_TEMPLATE/user-feedback.yml) and
triaged with these labels:

- `user-feedback` — raw input from a real user or testing session.
- `validated` — a recurring or confirmed problem worth acting on.
- `enhancement` — a resulting product change.
- `good first issue` — scoped for an external contributor.
- `help wanted` — open for community help.

Each feedback issue aims to capture:

- **Feedback source** — where the input came from (kept anonymous).
- **Observed problem** — what the user actually struggled with.
- **Frequency or repetition** — how often it comes up.
- **Current workaround** — what users do today.
- **Product implication** — what it means for the product.
- **Acceptance criteria** — what "resolved" looks like.
- **Related pull request** — the change that addressed it.
- **Release included** — where it shipped.

This turns informal input into visible, verifiable product evidence over time.
